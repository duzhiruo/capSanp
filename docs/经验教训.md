### [2026-07-17] 从同步硬编码到异步声明式 Agent Runtime

**背景：** v0.1 的 Agent 是一个 Organizer 函数，硬编码 3 步工具调用，在 HTTP 请求内同步阻塞执行。需要升级为企业级 Agent 运行时。

**问题：** 同步执行阻塞客户端；工作流硬编码无法扩展；任何一步失败整个 Run 丢失所有结果；零测试覆盖无法安全重构。

**根因：** v0.1 优先跑通闭环，没有考虑异步和韧性。这在 demo 阶段是合理的，但要往企业级走必须补上。

**解决方案：**

1. 声明式 Pipeline：定义 `StepDefinition`（步骤名、工具、超时、重试、失败策略）+ `AgentType`（步骤列表），通用 `AgentRunner` 按定义执行。
2. 异步 Worker：MySQL `agent_tasks` 表做任务队列，`SELECT FOR UPDATE SKIP LOCKED` 竞争消费。Worker 嵌入 API 进程。
3. Step 级韧性：每步独立超时/重试/降级。LLM 失败用 mock 结果降级继续（`FailContinueDegraded`），OCR 失败中止。
4. 优雅关停：Worker 用独立 `context.Background()` 执行任务，父 ctx 取消后完成当前任务再退出。

**教训：**

- Memory store 是天然的 test double。Repository 接口 + Memory 实现让所有测试不依赖 MySQL，这个模式在项目初期就定下来非常值得。
- Worker 测试中的计时问题：LLM 步骤配了 2 秒重试延迟，测试必须等够长时间。教训是测试异步行为时要考虑内部延迟叠加。
- 优雅关停的关键：任务执行要用独立 context（不继承父 ctx），否则取消信号会中断正在执行的任务。
- 异步 API 应返回 HTTP 202 Accepted，不是 200 OK — REST 语义细节但对客户端很重要。

**影响范围：** 跨项目通用（Agent Runtime 模式、异步任务队列模式、优雅关停模式）

### [2026-07-17] 统计 API + 链路追踪

**背景：** 企业级 Agent 运行时需要可观测性——每个请求能追踪完整链路，以及运营指标 dashboard 数据源。

**问题：** 日志分散无法关联同一请求的多次调用；缺乏运营数据（成功率、LLM 开销、队列健康度）。

**根因：** v0.1 的日志和数据模型没有 request_id 字段，也没有统计聚合能力。

**解决方案：**

1. 链路追踪：抽取 `reqctx` 独立包解决循环依赖，HTTP 中间件生成/透传 request_id，Worker 为每个任务独立生成 request_id，全链路 slog 带上 request_id。
2. 统计 API：`GET /v1/stats?range=today`，5 组指标（Agent/LLM/OCR/Queue/Screenshots），MySQL 实现用 6 条聚合 SQL，Memory 实现用内存遍历。
3. `agent_runs` 表加 `request_id` 列，HTTP 响应头回传 `X-Request-ID`。

**教训：**

- 循环依赖是 Go 项目分包的常见坑。`httpapi` 依赖 `agent`（用 NewID），`agent` 又需要 request_id context 操作。解法是提取公共包（`reqctx`），而不是在 `httpapi` 里定义 context key 再让 `agent` 导入。
- SQL 中 `timeRangeToSQL` 返回 SQL 函数字符串（如 `CURDATE()`）作为 `?` 参数会被当作字面量字符串，需要在 Go 端计算 `time.Time` 后传入。这是 prepared statement 的基本规则但容易疏忽。
- Memory store 的统计实现虽然是 O(n) 遍历，但作为测试 double 完全够用，且保证了与 MySQL 实现的接口一致性。
- Go 原生 string 不需要像 `fmt.Sprintf` 那样用 `%%` 转义 `%`。SQL LIKE 中直接写 `%` 即可。

**影响范围：** 跨项目通用（链路追踪模式、Go 循环依赖治理、统计聚合 API 模式）

### [2026-08-13] 向量搜索与语义搜索

**背景：** 关键词 FULLTEXT 无法覆盖「上次那个竞品定价」这类自然语言主题搜索，需要 embedding + 向量检索。

**问题：** 业务 ID（`shot_xxx`）不是合法 UUID，Qdrant Point ID 要求 UUID；向量库不可用时不能拖垮核心上传/整理流程。

**解决方案：**

1. Embedding Provider（DashScope OpenAI 兼容 `/embeddings`）+ Mock；Pipeline 第 4 步 `embedding.generate`，失败策略 `skip`。
2. `VectorStore` 接口：Qdrant 实现 + Memory 暴力余弦；业务 ID 经 SHA1 映射为确定性 UUID，payload 保留 `screenshot_id`。
3. 混合搜索：FULLTEXT 与 ANN 并行，RRF(k=60) 融合；Qdrant/Embedding 失败自动降级为关键词。
4. `cmd/backfill` 为存量截图补录向量。

**教训：**

- Qdrant Point ID 必须是 UUID，不能直接用业务字符串 ID；用确定性哈希映射，检索时从 payload 取业务 ID。
- 向量能力应作为可降级附件：`FailSkip` + 搜索 mode 降级，保证核心闭环不依赖 Qdrant。
- memory 预览模式应联动使用内存向量库，否则 embedding 步骤会因工具未注册而全部 skip。

**影响范围：** 跨项目通用（混合搜索 RRF、向量库抽象、RAG 基础设施）
